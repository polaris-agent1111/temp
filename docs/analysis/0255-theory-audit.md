# Task 0255 Theory Audit: 5发串行实战发射序列熔断机制与超时降级沙盘

## 1. 业务痛点与平台出分不确定性

官方每日提交额度仅限 5 发，且官方排行榜刷新出分通常存在 45~60 分钟的网络评测延迟。在决战日（11/08）多队伍密集提交时，评测后端可能发生排队积压甚至网络瞬断：
- 若调度程序死等出分，单次超时将导致后续所有提交被无限期阻断，白白浪费单日宝贵额度；
- 若无节制重试，一旦连上服务端将立刻消耗当日额度，甚至触发平台超额封号红线。

因此，必须设计一套**具有严格硬超时的自适应熔断降级有限状态机（Circuit Breaker State Machine）**。

## 2. 熔断降级状态转移逻辑

1. **时钟窗口监视**：每发射一次提交，启动 $T_{\text{timeout}} = 60\text{ 分钟}$ 倒计时；
2. **正常分支（$t \le 60\text{m}$ 出分）**：接收官方实际耗时，执行 1D 卡尔曼滤波更新背景信道后验状态，动态分派下一发候选树；
3. **熔断降级分支（$t > 60\text{m}$ 超时）**：
   - 触发 `TIMEOUT_CIRCUIT_BREAKER` 告警；
   - 自动判定信道处于重度竞争或平台拥塞，激活保守稳健先验；
   - 下一发自动降级为平原稳态树 `plateau-a` 或防御堡垒 `defense-fortress`；
   - 确保流水线无死锁，单日 5 发提交额度被 100% 完整打出。

## 3. 100 轮战役（500 发次）沙盘推演结果

- **战役完成率**：**100.0%**（100/100 战役全部打满 5 发并收敛）；
- **额度超限违规**：**0 次**（严格锁定 $\le 5$ 发/日）；
- **死锁挂起发生率**：**0 次**；
- **熔断降级成功介入**：103 次（在发生平台延迟积压时均成功执行保底自愈）。

## 4. 结论

熔断降级状态机在理论和仿真中完全闭环，杜绝了决战日因平台出分阻塞导致的停摆风险。
