## 1. 核心理论：CID 身份、路径验证与保活三层机制

QUIC 连接身份绑定在 **Connection ID（CID）** 而非四元组上（RFC 9000 §7.1/§9）：NAT 重映射外部端口后，服务器收到的包 CID 不变即视为**同一连接的路径迁移**，无需重新握手。围绕该机制有三层时间参数：

### 1.1 NAT 映射空闲超时（重绑定的根源）

UDP NAT 映射在空闲超过 $T_{\text{nat}}$ 后被回收，下一个包落在新的外部四元组上。模型取值（文献锚点）：

| 场景 | $T_{\text{nat}}$ | 权重 |
|---|---|---|
| Linux netfilter `nf_conntrack_udp_timeout` | 30 s | 0.4 |
| 常见家用路由器 | 60 s | 0.4 |
| Linux conntrack `udp_timeout_stream`（双向流） | 120 s | 0.2 |

关键观察：**下载活动期双向持续有包，映射永不过期**——重绑定只可能发生在下载间空闲间隙（gap）内。因此问题等价于「空闲间隙内的映射保活」。

### 1.2 保活间隔的充分条件（预防层）

空闲每达 $T_{\text{ka}}$（含发送抖动 $J \sim U(0,1)\,\text{s}$）即发 PING，同时刷新 NAT 计时与 QUIC 连接层 idle timer（RFC 9000 §10.1）。映射过期的充要条件是某一保活间隔超过 $T_{\text{nat}}$：工程准则取 $T_{\text{ka}} \le T_{\text{nat}}^{\min}/2 = 15\,\text{s}$（半超时裕度），对 30/60/120 s 三档全部免疫。保活同时把 QUIC 连接层空闲超时

$$T_{\text{idle}}^{\text{QUIC}} = \max(3 \times \text{PTO},\ \min(\text{both endpoints' min\_idle\_timeout}))$$

钉在永不触发——若对端通告较小的 `min_idle_timeout`，保活从「可选优化」升级为「必须项」。

### 1.3 路径验证的物理下界（恢复层）——v2 关键修正

映射一旦过期，按 RFC 9000 §8.1 服务器在新路径上发 PATH_CHALLENGE、客户端回 PATH_RESPONSE，验证完成恰需 **1 个完整 RTT**（CHALLENGE→RESPONSE 是往返，不是 v1 所称「半个 RTT」）；验证完成前服务器受**反放大限制（3×）**，下行为主的流量在此窗口内近似停滞。因此：

$$T_{\text{recovery}}^{\text{per-event}} = 1.0\,\text{RTT} = 70\,\text{ms} \quad (\text{物理下界，非调参可达})$$

**结论：0.5 RTT 的逐事件恢复时延在 RFC 9000 框架内不可达成；0.5 RTT 门禁只能以「预防」（事件数 = 0）达成，而非「更快恢复」。** 任何「0.38 RTT 自愈」类表述均属门禁写进模型的循环论证。

## 2. 仿真与统计验证

由 `zcode/scripts/keepalive0334_quic_migration.py` 开展蒙特卡洛仿真（seed=20261107，每配置 $n=10^4$ 会话，RTT=70 ms，6 下载会话、下载 $U(100,170)$ s、间隙 $U(5,90)$ s、会话首间隙 $U(0,60)$ s）：

| $T_{\text{ka}}$ | 重绑定/会话 | P(会话有事件) | 期望恢复 (ms/会话) | 逐事件恢复 | 一致性 | 保活开销 (KB/会话) |
|---|---|---|---|---|---|---|
| off | 2.337 | 76.0% | 163.58 | 70 ms | 100% | 0 |
| 30 s（不安全） | 1.563 | 39.0% | 109.38 | 70 ms | 100% | 0.171 |
| **15 s（推荐）** | **0.000** | **0.0%** | **0.00** | — | **100%** | **0.704** |
| 5 s | 0.000 | 0.0% | 0.00 | — | 100% | 2.252 |

- **消融实验**（$n=10^4$ 次下载中强制路径切换）：逐事件恢复 = **70.0 ms = 1.0 RTT**（0.5 RTT 门禁逐事件达成：**False**），一致性 100%，重新握手 0 次。
- **闭合形式交叉验证**：单间隙过期率仿真 0.70512 vs 理论 $P(g>30)=60/85=0.70588$；$T_{\text{ka}}=30$ 会话级均值 $N=10^5$ 独立种子下 1.6169 vs 理论 $0.4\times(5\times0.7059+0.5)=1.6118$（0.3% 吻合）。期望恢复 = 事件数 × 70 ms 精确守恒（163.58 = 2.337×70）。
- **状态一致性 100% 的机制来源**：状态向量（CID、TLS epoch、流控窗口、流偏移、丢包检测状态）跨迁移逐项携带并做不变量校验，迁移 $\ne$ 重新握手；$7\times10^4$ 会话 + $10^4$ 次强制切换中失同步 0 次、QUIC 连接层死亡 0 次（最大间隙 90 s < 120 s 模型空闲超时）。与 v1 的字面量 `True` 有本质区别。

## 3. 门禁审计结论

- **G1 重绑定恢复时延 ≤ 0.5 RTT（35 ms）**：**PASS（仅以预防口径）**。推荐工作点 $T_{\text{ka}}=15\,\text{s}$ 下重绑定事件数 = 0，期望恢复时延 0.00 ms ≤ 35 ms；逐事件恢复（强制切换消融）= 70 ms = 1.0 RTT > 35 ms，**逐事件口径下门禁物理不可达**，不得以「逐事件 0.5 RTT」或「0.38 RTT 自愈」话术对外表述。
- **G2 状态一致性 = 100%**：**PASS**。全部配置下 0 失同步、0 重新握手、0 连接死亡（由不变量校验得出，非硬编码）。
- 保活开销：$T_{\text{ka}}=15\,\text{s}$ 时 0.704 KB/会话，相对数百 MB 传输量占比 $\sim 10^{-6}$，可忽略。
- 验证脚本：`zcode/scripts/keepalive0334_quic_migration.py`；审计报表：`zcode/scripts/keepalive0334_output.json`（v1 的 `runs/nat0334_migration_keepalive.json` 系越界落盘，保留备查、不作为口径来源）。
- **适用性诚实声明**：iDSN 评测拓扑为固定 Linux netns/veth、端点静态，数据路径中**不存在 NAT 设备**，重绑定在当前评测中属假设场景。本分析的价值是报告答辩（Q&A）与协议健壮性设计依据，**不构成提分杠杆**，v1「完全消除中断风险」的说法据此降级。
