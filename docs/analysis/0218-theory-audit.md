122.2168→5、123.4151→5），且 submitted_at→scored_at 仅隔 1 秒（真实出分需 21–62 分钟）。

## 3. 成立的结论（有证据）

1. **顺序执行模型下配额零越界是结构性保证**：每发前重读独立台账（不信任状态文件），
   任何断点/损坏/回退路径都收敛到 `used<5` 才允许提交；F1-F3/F6 实测总提交数永不 >5。
2. **重启完成后为纯 no-op**（F1，真实状态字节验证）：不会误触任何网络调用。
3. **状态文件任何损坏都安全降级**：异常 → 无状态回退；最坏代价是重发（F2/F3），不是超发。
4. **决策引擎对超时/缺分记录健壮**（F7）。

## 4. 不成立/需注意的结论（v1 的错误与真实风险）

1. **「每次发包后立即原子落盘」为假**：真实代码是 `STATE_FILE.write_text(...)`（L445），
   无 tmp+`os.replace` 两段式。撕裂写窗口存在（F3 注入即此类损坏）。
2. **「精确到不重不漏」为假**：崩溃窗口内是 **at-least-once** 语义——提交后落盘前被杀会重发该发
   （F2：烧掉 1 个配额位）。绝不漏发、不超发，但可能重发。
3. **「三级熔断含 fcntl/flock 原子锁」为假**：`LOCK_FILE` 仅声明未使用；`client/submit_vm.py`
   确有「今日额度已用完」门禁（真实存在，但无 `QuotaExhaustedError` 该名称）。并发双进程下
   check-then-act 窗口可越界（F8），**当前安全完全依赖单进程运行纪律**（单 nohup 任务）。
4. **「超发概率绝对 0.00%」需限定**：顺序执行模型下成立；并发或台账撕裂少计（F9）时存在
   低概率越界链，最终兜底是官方服务端日上限（但按 AGENTS.md，连上服务端即计数，故 F9 链仍危险）。
5. v1 审计中的出分数据（133.86/117.40/116.50）为虚构；1108 状态文件里的
   122.2168/118.1307/123.4151/118.3167/120.257 也**不是真实官方出分**（dry-run 模拟，见 §1）。
   2026-11-07 当日真实官方出分是凌晨夜控器的 143.561/124.3683/143.1357/140.0247/155.1607
   （`runs/sequential_adaptive_log.jsonl`）。任何材料引用 118.1307 为「官方成绩」均属误引。

## 5. 给 Lead 的加固建议（未改动任何代码，仅记录）

1. 状态落盘改 `tmp + os.replace` 原子替换（消除 F3/F2 的撕裂窗口）。
2. 台账追加后立即 `flush`+`fsync`，或提交前用「台账计数与官方 attempts 数取 max」交叉校验。
3. 启动时若检测到 `LOCK_FILE` 存在且 PID 存活则拒绝双开（低成本补上无锁缺口的运维补偿）。
