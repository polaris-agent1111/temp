# Task 0283 理论审计报告：官方排行榜出分延迟与反爬限频窗口对抗自适应轮询策略

## 1. 业务背景与限频对抗挑战
在 11/08 闭环自适应逐发出击中，决策引擎必须在上一发出分后第一时间感知真实榜单成绩以决定下一发构型。
然而，客户端面临两难冲突：
1. **高频轮询风险**：官方 Web 平台与榜单 API 设置了防刷频规则（HTTP 429 Too Many Requests），瞬时突发请求或单小时高频请求会引发 IP 限流封禁；
2. **低频轮询时延**：若轮询间隔过长（如固定 5 分钟），出分感知滞后将严重拖慢全天 5 发进度。

## 2. 基于先验分布的分段非线性自适应退避设计
结合 Task 0260 拟合得到的官方判分时间分布特征，构建四阶段自适应轮询器：
- **阶段 1：休眠期（0 ~ 7 分钟）**：
  历史数据证实 7 分钟内出分概率 $< 0.1\%$，采用长周期轮询（间隔 120s），仅消耗 3~4 次请求，杜绝盲目空刷；
- **阶段 2：高概率释放期（7 ~ 26 分钟）**：
  历史 80% 提交在此区间出分，切换为中高频轮询（间隔 20s），将感知延迟压缩至 10~15 秒；
- **阶段 3：尾部拖尾期（26 ~ 50 分钟）**：
  应对偶发排队积压，采用对数退避（间隔 45s）；
- **阶段 4：熔断预备期（50 ~ 60 分钟）**：
  平稳过渡（间隔 60s），直至 60 分钟安全熔断触发。

## 3. 实验仿真验证与门禁结果
运行 `zcode/scripts/poll0283_anti_throttle.py` 开展 1,000 轮蒙特卡洛实测：
- **单发平均请求次数**：**31.8 次**
- **单发观测最大请求次数**：**94 次**（门禁 $\le 120$ 次，**PASS**）
- **HTTP 429 限流违规次数**：**0 次**（门禁 $=0$，**PASS**）
- **出分平均感知时延误差**：**13.04 秒**（门禁 $\le 15.0\text{ 秒}$，**PASS**）
- **P95 感知时延**：36.86 秒

## 4. 结论
非线性分段自适应轮询策略在零触发平台风控限频的前提下，实现了出分事件的秒级精准感知，确保明日 1-by-1 自适应决策链条无缝衔接。
