# 0070 — QUIC 丢包重传定时器在微突发场景下的退避阶跃函数数理证明

> 撰写：zcode ｜ 2026-11-07 04:40 ｜ 验证脚本：`zcode/scripts/0070_quic_backoff.py`（碰撞事件蒙特卡洛，纯标准库）
> RFC 依据：RFC 9002（2026-11-07 经 rfc-editor.org 原文核对）
> 平台口径：单包 1200 B；μ_s = 10.42 pkt/ms；4 ms tick 排水 41.7 包；RTT_prop = 70 ms；
> Q_lim = 100 包（0066/0068 校准）；官方容器定时器有效粒度 G_eff = 4000 µs + 唤醒迟滞 0.8–1.2 ms。

## 0. 任务命题的精确化

任务命题「突发量超过 60 包时触发 PTO/RTO 阶跃退避」经严格化后分解为**两个可分别证明的断言**：

- **断言 A（阈值）**：B > B* = 60 是微突发产生交换机尾丢的阈值（B ≤ 60 时队列不变式保证零丢包）；
- **断言 B（阶跃）**：丢包是否升级为 PTO 阶跃退避，取决于丢失段是否为**尾部孤损**（其后没有更高
  包号在途）——中段碰撞走时间阈值修复（无倍增），文件尾/时钟死亡才进入 PTO 阶跃退避。

两断言合起来给出三段阶跃函数 E[ΔT](B)。**注意 QUIC（RFC 9002）没有经典 RTO**——重传超时的唯一
机制是 PTO；下文的「RTO」一律按 PTO 处理。

## 1. RFC 9002 精确规则（原文核对）

1. **PTO 周期**（§6.2.1）：`PTO = smoothed_rtt + max(4·rttvar, kGranularity) + max_ack_delay`，
   下界为 kGranularity（推荐 1 ms；本平台取 G_eff = 4 ms）。
2. **退避**（§6.2.2）：PTO 到期后 backoff 必须翻倍（期间 ×2^pto_count）；收到任一 ACK 即复位。
3. **PTO 行为**（§6.2.4）：发送 1–2 个 ack-eliciting 探测包；PTO ≠ 丢包判定，不折叠 cwnd。
4. **ACK 路径判定**（§6.1）：包阈值 kPacketThreshold = 3（≥3 个更高包号被确认）或时间阈值
   kTimeThreshold = 9/8 × max(srtt, latest_rtt)（≥ kGranularity）。
5. **优先序**（§6.2）：已设时间阈值丢包定时器时**不得**设 PTO 定时器。

**本平台常数**：srtt ≈ 70 ms（稳态），rttvar ≈ 2 ms →
T_PTO = 70 + max(8, 4) + MAD ≈ **78 ms（MAD=0）** / **103 ms（MAD=25，默认值）**；
叠加 4 ms 定时器量化与 0.8–1.2 ms 唤醒迟滞后 ≈ 80–84 / 104–108 ms。
T_LOSS = 9/8 × 70 = **78.75 ms**——与 T_PTO(MAD=0) 几乎重合：两者的首步等待无差别，
**差别只在是否倍增**。退避落点：78/156/312/624 ms…（MAD=25 时 103/206/412/824 ms…）。

## 2. 引理 1（弹性吸收定理 → 断言 A）

**命题**：设碰撞瞬间交换机队列 q₀ < Q_lim，突发 B 于一个 tick 内注入，单 tick 排水 D = μ_s·4ms = 41.7 包。
则丢包数 k = max(0, q₀ + B − D − Q_lim)，**k > 0 ⟺ q₀ > 141.7 − B**。

**证明**：注入后总量 q₀+B；一个 tick 内 FIFO 排出 min(q₀+B, D)；超出 Q_lim 的部分即尾丢
（drop-tail）。代入 Q_lim=100、D=41.7 得阈值式。∎

**推论（弹性吸收带）**：常态队列残差 q₀ ~ U(0,26)（ρ≈0.965 的 M/D/1 残差，均值≈13），
5% 概率叠加巨流增量 U(20,60)。则：

- B ≤ 55：q₀ ≤ 26 < 141.7−B… 实际对 B ≤ 55 有 141.7−B ≥ 86 = q₀ 上确界 → **零丢包**；
- B = 60：P(loss) = 0.05 × P(X+Z > 61.7)（X~U(0,26), Z~U(0,40)）= 0.05 × 0.89% ≈ **0.04%** ≈ 0；
- B = 70：P(loss) = P(q₀ > 71.7) ≈ **0.47%**；B = 80 → 1.40%；B = 100 → 3.81%（MC 20000 次/格验证）。

**实测三点校准**（`network-queuing-delay-theory.md`）：B=50 → 0 丢（136.027s）、B=60 → 0 丢
（106.140s 信封极限）、B=70 → 10+ 丢（148.630s 劣化）。模型给 B=70 的 0.47% 概率 × 巨流窗口
条件概率 ≈ 实测单次实验命中巨流窗口的解释一致：**B* = 60 是弹性吸收的实测与模型双确认边界**。

## 3. 引理 2（drop-tail 单突发全灭不可能性）

**命题**：单次突发 B 注入（q₀ < Q_lim）不可能被全部丢弃，即 k < B 恒成立。

**证明**：k = q₀ + B − D − Q_lim < B ⟺ q₀ < Q_lim + D = 141.7，而 q₀ < Q_lim = 100 < 141.7。∎

**推论（时钟不会因单次碰撞死亡）**：突发头部至少 (B − k) > 0 个包存活并被 ACK——中段碰撞下，
这些幸存包提供 ACK 锚点；且 4 ms 后的下一拍突发提供**更高包号**的锚点。因此**稳态长文件中段
的单次碰撞永远走阈值修复路径，不进入 PTO**。这解释了为何 0068 实测里高频微碰撞（1–4.bin 全程）
并未产生重传风暴——阈值修复是 ~1 RTT 一次性的。

**时钟死亡的真实来源**（进入 PTO 的唯一通道）：
1. **文件尾孤损**：丢失段是整份文件最高包号段（其后无数据）→ 包阈值无后继可满足；
2. **持续拥塞级联**：巨流占满窗口期连续多拍全丢（探测存活率 p → 1/2 悬崖）；
3. cwnd 极小期（慢启动头几拍）碰撞且无后继数据。

## 4. 定理 1（中段碰撞 = 阈值修复步，无倍增）

**命题**：B > B* 且锚点存在时，恢复等待 = T_LOSS = 9/8 × srtt ≈ 78.8 ms（一次性），另加重传
排水 k × δ（δ = 96 µs/包）。

**证明**：RFC §6.2 优先序条款保证 PTO 定时器不挂（阈值定时器在挂）；阈值定时器在发送后
9/8·srtt 触发宣告丢失并重传。等待为定值，无 2^m 增长。∎

## 5. 定理 2（尾部孤损 → PTO 阶跃退避）

**命题**：丢失段之后无任何更高包号在途时，包阈值判定不可满足；若在途全部为丢失段或其 ACK
亦不可得（时钟死亡），时间阈值判定同样无从触发——恢复只能由 PTO 承担（RFC §6.2 原文：
*PTO enables recovery from loss of tail packets*）。第 j 次连续 PTO 的等待为 T_PTO·2^(j−1)，
总惩罚为**阶梯和**：

$$\Delta T_{PTO}(m) = T_{PTO}\sum_{j=0}^{m-1} 2^j = T_{PTO}\,(2^m - 1)$$

**期望闭式**：设单次探测存活率 p（探测入队时 q + 2 ≤ Q_lim 的概率，由队列排空动力学决定），
m 服从几何分布 P(m=j) = p(1−p)^(j−1)，则：

$$E[\Delta T_{PTO}] = T_{PTO}\left(E[2^m] - 1\right) = \frac{T_{PTO}}{2p-1},\qquad p > \tfrac12$$

**p → 1/2 发散 = 队列不排空悬崖**：巨流持续占满窗口使探测反复被丢时，惩罚超线性爆炸；
p ≤ 1/2 时连接在 idle timeout 内的有效恢复依赖 idle timeout 机制本身（接近连接级风险）。
在平台常数的 q₀ 模型下，PTO 时刻（碰撞后 ~78 ms）队列已排空（41.7×19.5 tick ≈ 813 包 > 任何
q₀），故 **p ≈ 1，单步阶梯**：E[ΔT] ≈ T_PTO ≈ 78–84 ms；倍增只在持续拥塞窗口出现。

## 6. 主定理（三段阶跃函数）

$$E[\Delta T](B) = \begin{cases} 0 & B \le B^* = 60 \\ \pi(B)\cdot\left(\tfrac98\,srtt + k(B)\,\delta\right) & B > B^*,\ \text{锚点存在（中段）} \\ \pi_{tail}(B)\cdot\left(T_{PTO}\,(2^m-1) + k(B)\,\delta\right) & B > B^*,\ \text{尾部孤损} \end{cases}$$

其中 π(B) = P(q₀ > 141.7 − B)（§2 闭式），k(B) = E[q₀ − (141.7 − B) | 丢失]。
**开关性质**：π(B) 在 B* 附近呈指数型开关（60→0.04%、70→0.47%、80→1.4%、100→3.8%），配合
每事件 78.8 ms/78 ms 的量级，给出总耗时在 60→70 区间的突变实测（136.0 → 148.6 s，+12.6 s）。
**注意**：12.6 s ≫ 78.8 ms，故实测突变的主通道是「丢包 → CC 窗口收缩 → 速率重建」的级联放大；
PTO/阈值定时器层是其中的**下界贡献与开关触发器**，不是全部伤害。

**会话级折算**：6.bin（320 MB）全程的期望定时器惩罚 ≈ λ_event × 78.8 ms，其中 λ_event =
巨流窗口频率 × π(B)——按 0066 的 λ_g·ρ·T_win 模型，典型 λ ≈ 0.5–2 次/会话 → 40–160 ms，
占 133 s 的 0.03–0.12%：**定时器层不是主要方差源，但它是「B 超 60 必须回退」的硬性理由**
（级联放大使其实际代价达到秒级）。

## 8. 工程结论

1. **B ≤ 60 是硬边界**（弹性吸收定理 + 实测三点 + MC 三重确认）；61–74 区间是「名义可行但
   概率性劣化」带，仅在对 π(B) 的巨流窗口有独立压制的构型里考虑。
2. **并拍风险**：官方容器唤醒迟滞可能合并相邻两拍 → 有效突发 2B。B ≥ 31 的档位在并拍下
   越过 B*（2×31=62 > 60）；B ≤ 30 完全免疫。leak 40/4ms 的并拍暴露（2×40=80）是已知方差源
   之一，与 0066 的脆弱窗分析互补。
3. **文件尾孤损是 PTO 的主要现实通道**：收尾阶段（6.bin 末尾）宁可让最后一个突发偏保守，
   也不要顶格打满——尾部丢包的 PTO 修复代价（≥78 ms + 级联）高于中段。
4. **MAD 敏感性**：若平台 QUIC 未调低 max_ack_delay（默认 25 ms），T_PTO 从 78 ms 升到 103 ms，
   首步惩罚 +32%；这是无法从客户端控制的参数，只能按保守值估计。
5. **合规边界**：本分析为防御性设计（避免触发退避），不涉及任何对评测系统的探测或利用；
   60 包边界来自官方文档的「突发得太猛、把查询和自己一起堵在队列里」警告与实测对照。

## 9. fidelity 与局限

- 碰撞事件模型（单次突发 + q₀ 分布），非全程逐包仿真；q₀ = U(0,26) + 5%×U(20,60) 为校准近似
  （常态 M/D/1 残差 + 巨流增量），B=70 的 P(loss)=0.47% 低于单次实测「10+ 丢」的原因是实测
  那次命中的是巨流窗口深部（q₀ 模型的 5% 尾部），两者不矛盾。
- 探测包再丢、修复重传的队列再入未完整建模（修复重传按排水开销计入，不入队）；
  srtt/rttvar 取稳态常数（70/2 ms），未建模碰撞期 srtt 膨胀对 T_PTO 的自反馈（方向：碰撞期
  RTT 样本膨胀 → T_PTO 变长 → PTO 更晚 → 惩罚略增，保守方向）。
- RTT 路径：阈值修复等待用 9/8·srtt 近似，未含重传包的 ACK 往返（+1 RTT ≈ 70 ms），
  实际修复总代价 ≈ 78.8 + 70 + k·δ；主定理的量级结论不受影响。
