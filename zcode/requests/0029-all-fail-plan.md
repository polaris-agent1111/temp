# 0029 — 全败预案：如果 11/06 五发全部 >130 怎么办

## 为什么

我们希望不会发生，但必须提前想好。如果自适应 5 发全部落在 130 以上（说明「本地最优区 = 官方最优区」这个假设崩了），11/07 的 5 发就必须换方向，不能再用同样的逻辑。

## 任务

产出 `report/预案-全败.md`：

1. **判定条件**：明确什么情况算「全败」（例如 5 发最好 >130，或 δ 全部 >8%）。
2. **至少 4 条完全不同的换向思路**，每条要具体到可提交的配置，并给出「为什么可能有效 / 风险 / 需要几发验证」：
   - 换模块（`token_bucket` 高余量族 / `origin` 大 burst / `coarse_grained_rate_based` 低 granularity）
   - 换 cap 量级（cap=rate+2 的最小桶 / cap=200 的超大桶）
   - 换间隔量级（2000/3000 的「半陷阱」区 / 8000/10000 的超长间隔）
   - 换「按文件分级」的结构（小文件激进、大文件保守，或反过来）
   - 其他你能论证的
3. **每条的判别成本**：需要几发才能证伪。
4. **优先级建议**：如果只有 5 发，投哪 5 个。
5. **一句话结论**。

## 约束

- 所有配置必须合法：`leak_interval_us >= 4000`（2000/3000 属于已知陷阱区，如果要用必须明确写清风险）、`bucket_cap >= leak_rate`。
- 不要建议重复投已知失败的配置。

## 禁止

不提交、不登录、不碰云主机、不改 `runs/`。
