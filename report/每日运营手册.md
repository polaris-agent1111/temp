## 一、每天的标准流程（5 步）

### ① 看前一天官方结果

```bash
python tools/official_log.py            # 拉榜单 attempts，与 submissions 配对 → runs/official_results.jsonl，打印表
python tools/official_log.py --cached   # 榜站 502 时改用本地已有快照（不联网）
```

- 读法：昨天 5 发各自出分了没、官方值多少、δ（官方/本地）落在哪档（正常 +2~3.5%；>10% 记「官方异常点」见 §三）。
- 榜站 502 不阻塞本步：提交服务器（client/submit_vm.py）与榜站是两回事，先记账后补榜。

### ② 生成次日候选

```bash
python tools/official_analysis.py           # 打印配对表/趋势/排名/候选（不写文件）
python tools/official_analysis.py --plan    # 追加生成 runs/submit_plan_<MMDD>_auto.json（规则：官方最好 rate±1 × cap±10）
```

- **auto 版永不覆盖手写版**：若 `submit_plan_<MMDD>.json` 已存在（Lead 手动/探测计划产出），auto 写 `*_auto.json` 供对照。
- 两个版本都看：探测计划.md 的自适应分支（按 11/06 官方最好点选 A/B/C/D 支）优先，工具 auto 版作交叉验证。

### ③ 人工确认后提交

```bash
python tools/submit_batch.py --plan runs/submit_plan_<MMDD>.json            # 预检 dry-run（只打印清单）
python tools/submit_batch.py --plan runs/submit_plan_<MMDD>.json --rehearse # 上传+格式检查，不投（推荐先跑）
python tools/submit_batch.py --plan runs/submit_plan_<MMDD>.json --yes      # 真提交（5 发逐个投，任一失败立即停）
```

- 逐发链路：`harness/upload_config.py`（生成+格式检查）→ `client/submit_vm.py --yes --note "tag | 说明"`；**失败即停**（rc=2 上传/格式失败，rc=3 提交失败/额度用尽）。
- **额度边界不在 00:00 时**（如跨日重置时间异常）用夜间脚本自带重试：

```bash
python tools/night_submit.py --plan runs/submit_plan_<MMDD>.json --at "YYYY-MM-DD HH:MM" --retries 3 --retry-wait-min 10
```

### ④ 记账与更新

```bash
python tools/official_log.py                                   # 新出分回填 runs/official_results.jsonl
# 手动重生成报告前半（工具输出段）：
python tools/official_analysis.py > /tmp/oa.md  # 取其输出段更新 report/官方探测分析.md 的「数据截至」头部
```

- 同步更新：`report/提交台账.md` §1 追加当日行；`report/官方探测分析.md` 数据截至时刻。
- 榜站恢复后：`python tools/official_analysis.py` 会自动读最新快照刷新榜首差距。

### ⑤ 写当小时报告

- 文件 `hourly/YYYY-MM-DD_HH00.md`（HH00=覆盖的起始整点），**固定五节**：
  1. 本小时做了什么（时间线，只写事实+结果）
  2. 关键数据（本地/官方/榜单，带数字）
  3. 当前进度（排名、额度、阶段）
  4. 下一步（可执行清单，≤5 条）
  5. 需要用户手动做的事（通常为「无」）
- 同步刷新 `hourly/INDEX.md` 为最新快照（排名表+关键指标）。
- 数字必须能在 `runs/results.jsonl`、`runs/submissions.jsonl`、`intel/raw/leaderboard_*.json` 对上。

## 二、每日检查清单（勾选式）

- [ ] **额度**：今日已用 __/5，剩余 __（硬上限 5；超 8 次可能封号）
- [ ] **出分**：当天 5 发**全部出分**？未出分的列出提交时刻，按 10–60 min 延迟判断是否异常（>2 h 走 §三）
- [ ] **对手**：榜单有无新纪录（重点：Catnet 126.965、光明未来、大肥鱼；用 `official_log.py` 打印或 0010 快照 diff）
- [ ] **榜站**：`GET /api/leaderboard` 是否 200（502 → §三第 1 行，不影响投递）
- [ ] **台账一致**：`runs/submissions.jsonl` 行数 = `runs/official_results.jsonl` 中已出分行数 + 未出分行数（配对无遗漏；`official_log.py` 会打印配对情况）
- [ ] **本地口径**：当日提交配置在 `runs/results.jsonl` 有 n≥3 本地样本（尖点不投）
- [ ] **文档**：台账/探测分析/hourly 三处已更新

## 三、异常处理表

| 异常 | 判定 | 处理 |
|---|---|---|
| **榜站 502**（提交服务器仍可用） | `GET /api/leaderboard` 非 200 | **继续投**（投递走 client/submit_vm.py，不依赖榜站）；`official_log.py --cached` 用快照记账；结果延后补。zcode 0010 每轮记录故障时长，恢复后补抓+对齐 |
| **提交报「已达到最大提交次数」** | 提交端返回额度拒绝 | 额度重置边界不在 00:00 → **等 10–20 min 重试**（`night_submit.py --retries 3 --retry-wait-min 10` 已内置）；重试仍失败则当日停投，明早再投，绝不绕限额 |
| **格式检查失败** | upload/format_check 报错 | **立即停投**（失败也扣额度！）→ 本地跑 `python tools/validate_pacer.py <question目录>` 修到 exit 0 → `--rehearse` 演练通过 → 再 `--yes`。常见坑：CRLF/末尾换行、timestamp≠目录号、burst<tokens、bucket_cap<leak_rate |
| **出分异常慢** | 提交 >2 h 无 attempts | 查 `official_log.py` 打印的 submission_log 有无该条（有=排队中，等；无=可能接收失败）→ 看榜站是否 502 盲区 → 仍无则查当日提交日志（桌面 `日期时间.log`），联系平台前先重跑一次 official_log |
| **官方成绩比本地差 >10%** | δ > +10% | **记录为「官方异常点」**（如 S5 +14.8%），**不要据此单点调整策略**；进 `official_analysis.py` 趋势时会被标注。只有同配置重投或邻域 2+ 点复现同方向才升格为信号（参 S5 的 rate 交互假说，待 11/06 裁决） |
| **本地评测跑出 80 s「假成功」** | total≈80 + 多文件 10.00 s 钳位 + valid=false | CRLF 换行坑 → 重新生成配置（LF、无末尾换行），过 validate_pacer 后重跑；该记录不进统计 |
| **配置下载失败/官方 0 分风险** | 任一文件下载失败 | 该次提交无成绩；停投查配置（leak_interval_us≥4000 铁律、cap≥rate），本地先复现 |

3. **每天 5 发打满但不冒险**：同最优配置可重复投（吃官方种子方差的下沿），单日 2 发异常（>最优+8 s）立即停投排查（0016 §4.3）。
4. **留 1 发兜底**：若当天前 4 发出现格式/链路异常，第 5 发留给「修好后的已知最优」，不用来试错。
5. **冻结前最后动作**：11/16 23:00 确认榜单快照留档（`intel/raw/`）、台账封行、复核材料包（`report/复核材料/`）与技术报告 v3 版本号核对——次日进入复核期（11/18 前）。
